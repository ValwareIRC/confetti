Confetti

a cozy editor for unrealircd.conf

UnrealIRCd's config is nested blocks all the way down. So Confetti draws them as nested trays — boxes inside boxes you can fold shut, arrange how you like, and read without knowing a single directive name. The real file sits alongside, updating as you go.

01 · The workspace

Boxes inside boxes, and the file beside them

Every block is a tray. Open one and its children are trays too, each a shade deeper into the cream, each with a slightly tighter corner and an edge that darkens to keep pace — so you can tell how deep you are without counting. Fold any of them shut and the header keeps telling you what's inside.

The right-hand panel is your actual file. Touch a value in a tray and the matching line lights up and rewrites itself; type in the file and the trays follow. Neither side is the "real" one.

Tray header

Never a bare arrow

Chevron, icon, plain name, real name, and — when it's shut — a summary of what's inside. 8 limits, 2 open, not encrypted. Folding something away never costs you information about it.

Depth

Five dots, always

Every tray header carries five pips with the filled ones showing how deep you are. Redundant with the tint and the corner radius on purpose — three signals for the same fact, so none of them has to be caught.

Arranging

It stays where you put it

Top-level trays are yours to drag around the canvas, and the layout is saved next to the config, not inside it. Nothing ever auto-arranges, reflows, or animates on its own.

Focus

One branch, nothing else

F on any tray and it fills the workspace — siblings gone, not dimmed, with a breadcrumb back. The single most useful control on the screen when a config has 17 blocks and you care about one.

02 · How deep it actually goes

Five levels. That's the whole ceiling.

Worth knowing before drawing anything, because it decides whether nested trays are a tidy finite design or an infinite-recursion problem. It's finite. UnrealIRCd's parser declares exactly four generations of child iterator — ce, cep, cepp, ceppp — and there is no cepppp anywhere in the source. A block plus four levels inside it is the hard limit.

5levels, maximum, ever
252places the parser reads a great-grandchild (ceppp)
0places it reads deeper than that
~12spots in the whole config that reach level 4 or 5

And nearly everything is shallow

Depth of the 183 directive paths the documentation gives its own heading to:

1 level37
2 levels104
3 levels40
4 levels2

So the deep case is real but rare, and it lives in a handful of known places. You can name them, hand-check that each looks right, and be finished — rather than building a general renderer and hoping.

/* every place a real config gets to level 5 */

set { restrict-commands { list { except { connect-time 60; } } } }      example.conf:572
set { anti-flood { everyone { handshake-data-flood { amount 4k; } } } }
set { tls { options { fail-if-no-clientcert; } } }
listen { options { websocket { allow-origin { kiwiirc.com; } } } }
link { outgoing { tls-options { options { … } } } }
operclass locop { permissions { channel { override { flood; } } } }   operclass.default.conf:25
spamfilter { … }                                                  spamfilter.conf:127
Exception

Operclass permissions want their own thing

It's the one deep structure that isn't a handful of settings — it's a wide tree of dozens of tiny on/off permissions. Five nested trays would be miserable. Give it a proper permission tree with checkboxes and inheritance shown, and treat it as a special case from the start.

Design

Five tiers, hand-tuned

Because the ceiling is five, each tier gets a designed look rather than a generated one: its own cream tint, corner radius, border weight and header size, checked side by side. A sixth tier can't happen, so nothing has to degrade gracefully.

03 · Two ways to say the same thing

Open a tray properly and it reads as a sentence

Values inside a tray are chips in running text, not fields in a form — because amount 4k; ban-action zline; ban-time 5m; is three facts about one decision, and a form pretends they're three separate ones. Click a chip, change it, watch the file change.

Ban their IP means

A zline — the connection is refused before UnrealIRCd does any work on it at all. Cheaper than a kline, and the right choice for something this early.

Both names, always

Plain name big, the real directive underneath in small mono. It costs one line and buys everything: you navigate by meaning, but the word you'd need to search the wiki, paste into a support channel, or recognise in an error message is right there. Nobody has to learn a private vocabulary that only this app speaks.

The plain names are the one genuinely hand-written part of the whole project — roughly 200 of them, one per block and per commonly-edited directive. Everything else is generated. Budget a proper afternoon for the wording, and let anything unnamed simply show its real name at full size.

04 · House rules

What keeps it readable

These aren't polish, they're the load-bearing part — a nested workspace goes bad fast without them, and each one is cheap if it's decided now rather than retrofitted.

  • Containment, never indentation. A visible box edge is unambiguous; four spaces of whitespace is something you have to measure with your eyes. Every level gets a real border.
  • Say everything three times. Depth is tint and radius and pips. A problem is an amber edge and an icon and a sentence. Never colour alone — that's colourblind-safe and it's less to hold in your head.
  • Nothing moves unless you moved it. No auto-layout, no reflow on open, no ambient motion, no things sliding in. A tray is where you left it, this session and next.
  • Collapsed still speaks. Every folded tray shows a summary. If it can't summarise itself in four words, that's a sign the grouping is wrong.
  • Messages wait for you. No toasts that disappear, no timed anything. Warnings sit in the console until dismissed, and dismissing is a click, not a countdown.
  • One branch at a time is always available. Focus mode isn't an extra — it's the escape hatch when the whole workspace is too much at once.
  • Density is a setting. Comfortable by default, with roomier and tighter available, because the right amount of visual information genuinely differs person to person.
05 · Where the words come from

Both halves already ship in the repo

A config editor is only worth using if it knows what every directive means, and hand-writing four hundred descriptions would rot within a release. It doesn't have to. UnrealIRCd answers this twice over, in its own source tree.

Structure

src/conf.c + 46 modules

440 comparisons of the form strcmp(cep->name, "…"). Scrape them at build time and you have every block, every directive and exactly how they nest — taken from the parser itself, so it cannot disagree with the server.

Meaning

doc/unrealircd_wiki.zim

428 articles in a 1.4 MB archive sitting in the source tree. Configuration/en alone is the complete reference, with one heading per directive — literally set::anti-flood, class::sendq. Bundle it and every hint works offline.

Joined on

the :: path

Names and nesting from the C, prose from the wiki, matched on the block::item notation both already use. That same path is the tray's subtitle, the search box's input, the error's jump target and what "copy path" puts on your clipboard.

Keep up by version, not by recency

The obvious move is to ask the live wiki for the current page on each directive. Don't. The live wiki documents the newest UnrealIRCd — which is not the one you're configuring. It will happily describe directives your 6.1.x doesn't have and quietly drop notes about ones it does.

The ZIM is better precisely because it's frozen. It's refreshed once per release — the commits say so in as many words, "Update doc/unrealircd_wiki.zim for 6.2.3" — and it carries metadata proving which snapshot it is. So the copy sitting in a server's own tree is, by construction, the documentation for the UnrealIRCd running on that server.

Caveat

It isn't in the installed tree

make install copies six doc files and the ZIM isn't among them — it lives in the source directory you built from. That's usually still sitting on the box, since UnrealIRCd's own upgrade script builds in place. Usually isn't always.

Fallback

Ship packs, fetch by version

When it isn't there — a Windows installer box, a tidied-up server — fall back to a cached pack keyed by release, fetching that release's pack if it's missing. That's the automation worth having: fetch 6.2.1's docs for a 6.2.1 server, never "the latest".

Fallback

Say when it's approximate

If the closest pack is 6.2.1 and the server is 6.2.3, the hint panel says so in a line, once, rather than presenting a guess as fact. Same for a directive the schema knows but the docs don't mention.

Bonus

The schema pins too

A pack is a pair — the ZIM plus the schema scraped from that release's conf.c. Pinning both together is what makes the whole version-drift problem go away instead of moving it.

The hand-written layer

On top sits the only part needing judgement: about thirty value types the docs imply but never formalise. Each is a chip that can't be got wrong.

06 · Getting to the file

Local and remote are one screen

This computer is always in the list, and every SSH host you add sits beside it. Pick one, browse, open. Nothing downstream knows or cares which it was.

The tree does one thing a file browser doesn't: it reads the include lines. An UnrealIRCd config is rarely one file — the shipped example pulls in six — so you see the real set, nested under whatever includes them.

Finding the control script

Looks for ./unrealircd beside conf/, or bin\unrealircdctl.exe on Windows, and runs version once. That answer picks the schema version and unlocks the buttons. Not found is fine — you get an editor.

Edge case

Includes over HTTPS

UnrealIRCd can include a URL. Those appear with a globe and open read-only, because the file lives on someone else's web server. Saying so plainly beats a mysterious failure to save.

07 · The workbench

The shell buys more than file access

Files only was the right call — JSON-RPC needs the server already running, which is exactly when you don't need this app. But once there's a shell, the unrealircd control script is sitting right there, and it does considerably more than rehash.

08 · The quest line

Get a server on the air

09 · The hard part

Never hand back a file you wouldn't recognise

This kind of tool earns trust once and loses it the first time it eats a comment. The shipped example is two thirds comments — carefully written ones, plus whatever you added at 3am. So the parser can't be an ordinary parser.

  • Parse to a lossless tree, not an AST. Every comment, blank line, tab and choice between # and // is a node with a byte range. Re-serialising an untouched file returns it byte for byte — that's the first test to write, run over every .conf in doc/conf/.
  • Edit the smallest range that works. Changing a chip rewrites the bytes of that one value. Lines you didn't touch are never reformatted, however wrong their indentation looks.
  • New blocks land at the end of the file they belong to, indented to match that file's own style, with one comment line saying what added them and when.
  • Deleting comments out first. The tray goes struck-through, the block gets commented; a real delete takes a second confirm.
  • Diff before write, always. Not buried — it's the first thing Save shows you, over SFTP exactly as locally.
  • Write atomically, keep one backup. Temp file, fsync, rename, and unrealircd.conf~ alongside. A half-written config on a live server is the worst outcome available.
10 · If you build it

Order, and what will bite

Each step is usable on its own, which matters — the schema work is the long pole and you want something in your hands while it runs.

  1. The lossless parser and its round-trip test. Nothing else is safe to build on. It either passes on every shipped config or it isn't done.
  2. The scraper and the pack format. conf.c and the 46 modules to a skeleton schema, a ZIM reader for the prose, and the resolver that picks a pack from unrealircd version. The ZIM format is small and well documented — a reader is a couple of hundred lines.
  3. Five tiers of tray, on real data. Point it at example.conf and draw it. This is where the design is proved or isn't, and it needs no SSH, no schema types, no editing.
  4. Chips and the two-way file panel. Types, plain names, editing, diff, save.
  5. SSH and SFTP. Connection manager, tree, remote save.
  6. Workbench and quests. Both are thin once there's a shell.
Risk

SSH auth on Windows

Don't shell out to ssh. You've been bitten by git-bash's ssh not seeing the Windows agent — same trap, one layer down. Use a library that speaks the protocol in-process and talks to the agent itself, with key file and password as first-class options.

Risk

A box with no ZIM

Docs packs solve version drift, but only where a pack exists. Windows installer boxes have no source tree at all. Build the fallback chain in step 2, not later — and always keep an unknown directive editable as raw text rather than hiding or dropping it.

Risk

Multiple set blocks

Two or three set blocks is normal and correct, and 6.1.1 added per-security-group overrides like set unknown-users { }. Draw one tray per block as written — never merge them — and let search be how you find a setting.

Shell

What to build it in

Tauri gives you a Rust core for SSH, SFTP and the parser, a web front end you can theme exactly like ircuitry, and small binaries on both Windows and Linux. Electron works too and buys the Node ecosystem — at the cost of shipping a browser.
